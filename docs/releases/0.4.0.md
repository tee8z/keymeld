# KeyMeld 0.4.0

Upgrade to **0.4.0** for the authorization and security fixes across the SDK, gateway, and enclaves.
Versions through `0.3.5` lack these protections.

## Security changes

- Participant registration requires an independent slot credential and an enclave-verified proof of key possession.
- Claimed slots are immutable; clients verify the participant roster and aggregate keys.
- Signing authority and required participant approvals bind the complete signing batch.
- Enclave commands and responses are authenticated, bound to the current boot, and protected against replay.
- SDK custody operations verify fresh Nitro attestation against trusted image measurements before sending secrets.
- Production KMS calls require Nitro recipient attestation and encrypted responses, with a pinned key ARN, AWS endpoint, and TLS roots.
- Signing approvals are required by default; unattended delegation requires an explicit opt-out.
- Gateway admission limits bound API mutations and attestation work; browser origins require an explicit CORS allowlist.
- Standalone-key operations require operation-specific proofs; request replay protection persists across gateway restarts.
- Operator pages require a separate credential; static-file requests cannot traverse outside the asset directory.
- Unsupported adaptor `And`/`Or` combinations are rejected, adaptor nonces use complete identities, and subset aggregate decryption is corrected.

See the [complete finding inventory](https://github.com/tee8z/keymeld/blob/v0.4.0/docs/AUTHORIZATION.md#finding-inventory).

## Upgrade

Upgrade the SDK, gateway, and enclaves together.
Archive legacy databases and enclave state, then create fresh sessions with the new authorization credentials.
Provision the gateway command credential and trusted enclave measurement policy before startup.
Integrations must retain registration and signing credentials separately from the shared session secret.

Follow the [migration guide](https://github.com/tee8z/keymeld/blob/v0.4.0/docs/AUTHORIZATION.md)
and [security configuration](https://github.com/tee8z/keymeld/blob/v0.4.0/docs/SECURITY_OPERATIONS.md).

## Deployment scope

Local verification covers cryptographic and HTTP regressions, attack scenarios, and recovery after gateway and enclave restarts.
Nitro hardware deployment needs its own acceptance results.
The [KMS guide](https://github.com/tee8z/keymeld/blob/v0.4.0/docs/KMS.md#current-trust-boundary) describes the attested recovery path and locked policy requirements.
The policy template is prepared for review; release artifacts do not configure an AWS account automatically.
