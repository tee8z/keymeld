# KeyMeld 0.7.0 (beta)

This release adds key deposits: a participant can seal a registration before the session it will join exists, and a later session registers it. Applications use this to accept entries first and form sessions from them afterwards, such as pools split from a queue.

## Changes

- **Deposit-scoped sessions.** `SessionAuthorizationManifest.deposit_scope` names a `DepositScope`: a deposit session id and a 32-byte digest that stand in for the session id and manifest digest, and opaque application evidence of at most 64 KiB (`MAX_DEPOSIT_EVIDENCE_BYTES`). `SignedSessionManifest::registration_scope()` returns the scope that registrations and escrow policies are bound to.
- **Deposits.** `RegistrationEnvelope::deposit` and `deposit_with_escrow` seal a deposit, and the SDK adds `UserCredentials::prepare_deposit_registration` and `prepare_deposit_registration_with_escrow`. A deposit carries its own possession-proof domain: a deposit-scoped session accepts only deposits, and no other session accepts them. The session auth key derives from the deposit session id.
- **Escrow commands.** For a deposit-scoped policy, `RequestContext.keygen_session_id` names the session the command acts in. Receipts stay bound to that session, because one deposit may be registered in more than one.
- The escrow verifier reads the evidence from the manifest it already sees at enrollment and binding. Nothing in the verifier interface changed.
- Keys registered as deposits cannot be exported to an unrestricted signer.

## Upgrade

Point at the new tag:

```toml
keymeld-sdk = { git = "https://github.com/tee8z/keymeld", tag = "v0.7.0", features = ["client", "dlctix"] }
keymeld-core = { git = "https://github.com/tee8z/keymeld", tag = "v0.7.0" }
```

Code that builds these types with struct literals must set the new fields:

- `SessionAuthorizationManifest { deposit_scope: None, .. }`
- `RequestContext { keygen_session_id: None, .. }`

Sessions without a deposit scope behave as before, and their JSON encodings, signatures and digests are byte-identical to 0.6.x.

The gateway and enclaves exchange bincode messages whose layout gains the new fields. Upgrade the gateway and every enclave build, including application enclaves built on `keymeld-enclave`, together. Persisted state is JSON and needs no migration.

Rebuild enclave images from this tag. On Nitro that changes their measurements: update any pinned PCRs before routing sessions to the new images.

## Beta status

This release retains the 0.4.0 beta limitations.
Validation uses simulated TCP enclaves and a mock KMS.
Real AWS Nitro hardware acceptance remains incomplete; use test keys and test funds only.
